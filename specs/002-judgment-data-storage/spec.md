# Feature Specification: 判決資料儲存目錄

**Feature Branch**: 未建立（無 `before_specify` hook；以規格目錄 `002-judgment-data-storage` 識別）

**Created**: 2026-11-06

**Status**: Draft

**Input**: 使用者提供之需求（原文）：

> judgments相關資料放在/data/judgments

**需求解讀**: 所有與判決相關的檔案資料，包括下載的原始檔、清洗後文本、Parquet 資料集、儲存清單與暫存檔，均以 `/data/judgments` 為唯一根目錄。此功能補充 `001-judgment-rag-search` 的資料處理與索引需求，定義資料在檔案系統中的落點、目錄結構、寫入完整性、容量監控、備份還原與遷移方式。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以固定根目錄統一判決資料 (Priority: P1)

維運人員在部署時將判決資料根目錄設為 `/data/judgments`。資料下載、清理、切分、Parquet 產出、索引建置與 RAG 檢索元件都從這個位置讀寫，不再將判決檔案散落在其他路徑。

**Why this priority**: 固定且唯一的資料根目錄是備份、容量監控、權限控管與資料追溯的基礎。位置不一致會導致資料遺失、重複處理與檢索結果不完整。

**Independent Test**: 在全新環境中將 `/data/judgments` 掛載為可寫入目錄，執行一次完整資料匯入，逐一檢查所有產出的判決檔案皆位於該根目錄下；再檢查各元件設定的有效根目錄是否一致。

**Acceptance Scenarios**:

1. **Given** 全新環境且 `/data/judgments` 可寫入，**When** 執行判決資料匯入，**Then** 原始檔、清洗後資料、Parquet 檔與儲存清單都建立在 `/data/judgments` 的子目錄中。
2. **Given** 根目錄設定為 `/data/judgments`，**When** 任一元件讀取判決資料，**Then** 該元件使用此根目錄，且系統中不存在其他判決資料路徑。
3. **Given** 某元件試圖將判決資料寫到根目錄以外，**When** 執行寫入，**Then** 系統拒絕該操作並記錄違規事件。
4. **Given** 根目錄不存在或不可寫入，**When** 系統啟動或執行匯入，**Then** 系統以明確錯誤停止相關作業，且不在其他位置產生部分檔案。
5. **Given** 管理者需要變更根目錄，**When** 送出新的路徑設定，**Then** 系統先驗證新路徑可用，再切換設定並留下稽核紀錄。

---

### User Story 2 - 目錄結構、原子寫入與清理 (Priority: P2)

維運人員與資料處理流程遵循一致的子目錄結構；每次寫入都是完整或不存在，中斷時不會留下損壞檔案；暫存檔只存在於根目錄內並會被清理。

**Why this priority**: 資料損壞與暫存檔堆積會直接影響檢索正確性與磁碟可用性，是穩定運作的必要條件。

**Independent Test**: 在匯入過程中強制終止行程，確認讀者看不到半寫入檔案；檢查暫存目錄在成功與失敗後都被清理，且根目錄外沒有任何暫存檔。

**Acceptance Scenarios**:

1. **Given** 根目錄已存在但子目錄缺漏，**When** 執行匯入，**Then** 系統自動建立所需子目錄後才開始寫入。
2. **Given** 寫入過程中行程被終止，**When** 重新啟動並檢視資料目錄，**Then** 不存在可見的半寫入或損壞檔案。
3. **Given** 匯入成功或失敗，**When** 檢查暫存目錄，**Then** 該次作業的暫存檔已被清理，且根目錄外沒有暫存檔。
4. **Given** 檔案路徑包含 `..`、絕對路徑或指向根目錄外的符號連結，**When** 嘗試寫入，**Then** 系統拒絕操作。
5. **Given** 任一判決檔案完成寫入，**When** 查詢儲存清單，**Then** 可取得其相對路徑、大小、校驗碼、來源與資料版本。

---

### User Story 3 - 容量監控、備份還原與資料遷移 (Priority: P3)

維運人員能查看根目錄的容量與健康狀態，在磁碟將滿前收到警告；可對根目錄建立一致性備份並還原；既有資料可從舊位置安全遷移到 `/data/judgments`。

**Why this priority**: 這些是營運持續性能力，可在核心資料流程穩定後補強，但缺乏時仍會影響長期可用性。

**Independent Test**: 模擬低磁碟空間、掛載失效、備份還原與舊路徑遷移，確認系統能告警、拒絕不安全寫入、通過校驗並可回滾。

**Acceptance Scenarios**:

1. **Given** 系統正常運作，**When** 維運人員查看儲存狀態，**Then** 可看到根目錄路徑、掛載狀態、讀寫狀態、已用與可用空間、最後成功寫入時間。
2. **Given** 可用空間低於設定門檻，**When** 執行匯入前檢查，**Then** 系統顯示警告，並在空間不足時拒絕匯入或要求管理者確認。
3. **Given** 根目錄資料完整，**When** 執行備份與還原，**Then** 還原後的檔案數量與校驗碼與備份清單完全一致。
4. **Given** 資料仍位於舊路徑，**When** 執行遷移，**Then** 系統複製並校驗資料後才切換至 `/data/judgments`；失敗時可回復使用舊路徑。
5. **Given** `/data` 掛載失效，**When** 系統偵測到挂載異常，**Then** 停止寫入、標示儲存狀態為降級或不可用，且不寫入底層替代目錄。

---

### Edge Cases

- `/data` 未掛載，但 `/data/judgments` 目錄仍存在於根檔案系統時，系統如何避免把資料寫進錯誤位置？
- 根目錄權限不足、擁有者錯誤或唯讀掛載時，系統如何處理？
- 寫入過程中磁碟剛好寫滿，已完成的檔案與儲存清單如何保持一致？
- 網路檔案系統暫時斷線或延遲過高時，如何避免誤判寫入成功？
- 路徑包含空白、Unicode 或特殊字元時，如何確保正確解析？
- 符號連結指向根目錄外部時，如何拒絕存取？
- 兩個匯入流程同時啟動時，如何避免互相覆蓋？
- 遷移或備份過程中斷時，如何續傳、重試或回滾？
- 根目錄在匯入期間被管理者變更時，進行中的作業如何處理？
- 備份期間仍有寫入發生時，如何取得一致性快照？
- 清理舊資料時，如何避免刪除現行版本或仍被索引引用的檔案？

## Requirements *(mandatory)*

### Functional Requirements

#### 根目錄與路徑一致性

- **FR-001**: 所有判決相關檔案 MUST 位於 `/data/judgments` 或其子目錄；系統預設根目錄即為 `/data/judgments`。
- **FR-002**: 根目錄 MUST 可集中設定；所有資料下載、處理、索引建置、RAG 檢索與維運元件 MUST 使用同一個有效根目錄，不得各自硬編碼其他判決資料路徑。
- **FR-003**: 系統 MUST 在啟動時及每次寫入前解析根目錄的實際路徑，確認其存在、可讀寫，且為預期的持久化掛載位置。
- **FR-004**: 根目錄不存在時，系統 MUST 嘗試建立；若無法建立或無權限，MUST 以明確錯誤停止相關作業，不得改寫到替代路徑。
- **FR-005**: `/data` 未掛載或掛載失效時，系統 MUST 偵測並停止寫入，避免將資料寫入底層空目錄。
- **FR-006**: 根目錄變更 MUST 僅限授權管理者執行；變更前 MUST 驗證新路徑可用，變更後 MUST 留下稽核紀錄。

#### 目錄結構與寫入完整性

- **FR-007**: 根目錄 MUST 至少包含原始資料、清洗後資料、Parquet 資料、儲存清單與暫存檔等子目錄；實際名稱可於規劃階段定義，但必須文件化並保持穩定。
- **FR-008**: 系統 MUST 在寫入前建立缺漏的子目錄；若建立失敗，MUST 在寫入任何檔案前停止作業。
- **FR-009**: 所有檔案寫入 MUST 採原子性方式完成；讀者不得看到半寫入、截斷或損壞的可見檔案。
- **FR-010**: 暫存檔 MUST 位於根目錄內的暫存子目錄；無論作業成功或失敗，MUST 清理該次作業的暫存檔，且不得在根目錄外產生暫存檔。
- **FR-011**: 每個完成的判決檔案 MUST 記錄於儲存清單，至少包含相對路徑、資料類別、大小、校驗碼、來源、資料版本與建立時間。
- **FR-012**: 系統 MUST 拒絕路徑穿越、絕對路徑注入，以及解析後指向根目錄外的符號連結。
- **FR-013**: 同一時間 MUST 只允許一個匯入流程寫入根目錄；並行請求 MUST 排隊或拒絕，避免檔案與清單不一致。
- **FR-014**: 清理或刪除檔案時，系統 MUST 保護現行資料版本與仍被索引引用的檔案，並記錄刪除的路徑、原因與時間。

#### 容量、監控與生命週期

- **FR-015**: 系統 MUST 提供儲存狀態，至少包含根目錄路徑、掛載狀態、讀寫狀態、已用空間、可用空間、總容量與最後成功寫入時間。
- **FR-016**: 系統 MUST 在啟動時及運作期間定期檢查儲存健康狀態；異常 MUST 於 30 秒內反映於狀態資訊。
- **FR-017**: 可用空間低於設定門檻時系統 MUST 發出警告；預設門檻為總容量 10% 或可用空間 20 GB，以較嚴格者為準，門檻可由管理者調整。
- **FR-018**: 匯入前系統 MUST 估算所需空間並與可用空間比較；空間不足時 MUST 拒絕匯入或要求管理者明確確認。
- **FR-019**: 寫入失敗或磁碟寫滿時，系統 MUST 保留既有的完整檔案與儲存清單，標示失敗的檔案與階段，並允許在空間恢復後重試。
- **FR-020**: 資料保留與清理 MUST 依管理者設定的政策執行；現行版本與仍被引用的資料不得被自動清除。

#### 備份、還原與遷移

- **FR-021**: 系統 MUST 能對根目錄建立一致性備份，排除暫存檔，並包含儲存清單與校驗碼。
- **FR-022**: 還原時系統 MUST 驗證檔案數量、校驗碼與資料版本；驗證失敗時 MUST 拒絕還原，且不得破壞現有資料。
- **FR-023**: 系統 MUST 支援將既有判決資料從舊位置遷移至 `/data/judgments`；遷移完成並通過校驗後才切換讀寫路徑。
- **FR-024**: 遷移 MUST 可重試且具冪等性；失敗時 MUST 能回復使用舊位置，且不得產生重複或損壞資料。
- **FR-025**: 遷移、備份與還原 MUST 產生包含處理數量、位元組數、校驗結果、耗時與狀態的摘要，供管理者查詢。

#### 安全與稽核

- **FR-026**: 只有服務帳號與授權管理者能讀寫根目錄；權限 MUST 採最小授權原則。
- **FR-027**: 系統 MUST 記錄儲存相關事件，包括根目錄變更、權限錯誤、遷移、備份、還原與刪除；紀錄不得包含判決檔案內容。
- **FR-028**: 根目錄設定、遷移與刪除操作 MUST 具備可追溯的稽核紀錄，至少包含操作者、時間、動作與結果。
- **FR-029**: 儲存狀態異常或儲存清單不一致時，系統 MUST 進入降級或唯讀模式，不得覆寫可能仍有效的資料。
- **FR-030**: 系統 MUST 在啟動時驗證根目錄與儲存清單的一致性；不一致時 MUST 告警並提供修復或重建選項。

### Key Entities *(include if feature involves data)*

- **資料根目錄設定 (Data Root Configuration)**: 判決資料根目錄路徑、生效時間、變更者與驗證狀態；預設為 `/data/judgments`。
- **判決資料檔案 (Judgment Data File)**: 位於根目錄下的檔案；包含相對路徑、資料類別、大小、校驗碼、來源、資料版本與建立時間。
- **儲存清單 (Storage Manifest)**: 某個資料版本的檔案清單、校驗碼、產生時間與版本識別。
- **暫存工作區 (Ingestion Workspace)**: 單次匯入使用的暫存目錄與作業識別；包含建立、清理與失敗狀態。
- **儲存健康狀態 (Storage Health)**: 根目錄掛載狀態、讀寫可用性、容量、最後檢查時間與異常原因。
- **備份快照 (Backup Snapshot)**: 備份識別、建立時間、檔案數量、大小、校驗結果與保留期限。
- **遷移作業 (Migration Job)**: 舊路徑、目標路徑、處理數量、校驗結果、狀態與回復資訊。
- **儲存稽核事件 (Storage Audit Event)**: 操作者、時間、動作（設定變更、遷移、備份、還原、刪除）、結果與相關路徑。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 檔案系統稽核結果顯示 100% 的判決相關檔案位於 `/data/judgments` 下，根目錄外有 0 個判決檔案。
- **SC-002**: 在具備預設目錄與正確權限的全新環境中，完整匯入可在不手動建立子目錄的情況下成功完成。
- **SC-003**: 根目錄缺漏或不可寫入時，系統在 5 秒內回報明確錯誤，且產生 0 個部分寫入檔案。
- **SC-004**: 在寫入過程中強制終止行程的測試中，讀者可見的損壞或半寫入檔案數為 0。
- **SC-005**: 在路徑穿越與符號連結逃逸測試中，成功寫出根目錄外的次數為 0。
- **SC-006**: 可用空間降至設定門檻時，100% 的匯入前檢查會顯示警告；空間不足時 0 次在未警告的情況下繼續匯入。
- **SC-007**: 備份後還原的檔案數量與校驗碼 100% 與備份清單一致。
- **SC-008**: 從舊路徑遷移 100% 的資料後，遺失檔案數為 0，且可在失敗時回復至舊路徑。
- **SC-009**: 維運人員能在 1 分鐘內取得目前根目錄、容量使用率與儲存健康狀態。
- **SC-010**: `/data` 掛載失效後 30 秒內，系統狀態反映異常，且異常發生後對根目錄的寫入次數為 0。
- **SC-011**: 100% 的已儲存判決檔案可透過儲存清單追溯至來源與資料版本。
- **SC-012**: 同時啟動多個匯入請求時，僅 1 個寫入流程執行，且測試後損壞檔案數為 0。
- **SC-013**: 100% 的根目錄變更與遷移、刪除操作都有對應的稽核紀錄。
- **SC-014**: 儲存異常測試後，既有完整檔案與檢索資料的損壞數為 0。

## Assumptions

- 部署環境為 Linux 主機或容器，`/data` 為持久化磁碟區，服務帳號對 `/data/judgments` 具備讀寫權限。
- 本功能所稱「judgments 相關資料」包含原始下載檔、清洗後文本、Parquet 資料集、儲存清單與暫存檔。PostgreSQL 與 Qdrant 的服務資料目錄由各自服務管理，不在本功能的搬移範圍；其內容仍由 `/data/judgments` 的檔案匯入。
- 若使用者要求 PostgreSQL 或 Qdrant 的實體資料目錄也必須位於 `/data/judgments`，需另立功能處理，因為這涉及服務層級的資料目錄設定與停機遷移。
- 檔案系統支援原子 rename 與檔案鎖定；若使用網路檔案系統，必須支援等效的鎖定與一致性語意。
- 備份目標位於 `/data/judgments` 之外，且具備足夠容量。
- 既有判決資料可能位於舊路徑，首次導入時需要執行一次性遷移。
- 備份預設每日執行一次並保留 30 天，實際排程與保留期由管理者調整。
- 系統同一時間僅允許一個匯入流程寫入根目錄。
- 路徑區分大小寫，且以 POSIX 路徑語意運作。
- 磁碟加密、金鑰管理與基礎設施層級的備援由部署平台負責。

## Out of Scope

- 搬移 PostgreSQL、Qdrant 或其他資料庫服務的實體資料目錄。
- 雲端物件儲存、跨區域複寫或多站點同步。
- 磁碟加密、金鑰管理與硬體層級備援。
- 應用程式部署、容器编排或基礎設施即程式碼的實作。
- 清理 `/data` 下與判決無關的其他資料。
- 資料庫服務本身的備份與還原。
- Windows 路徑格式與跨平台檔案系統行為。
