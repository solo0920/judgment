# Holdout 題目建置計畫

**Status**: Not started；production 目前 holdout = 0 題。

**目的**: 建立一組不由代理、LLM 或 shared 題目轉換而來的人工 holdout，用於大改動前後各跑一次，判斷系統是否真的變好。

## 1. 使用邊界

- shared 的 25 題只能稱為「開發集」或「回歸測試」，不得對外稱為 holdout 或準確率基準。
- holdout 題目必須由人撰寫、人工核對官方現行法規／命令原文；不得由 LLM 生成後直接採用。
- 題目與標準答案寫完後鎖定版本；任何修改都要留下版本與理由。
- holdout 題目、逐題答案與失敗明細不得進入 Agent JSONL、代理 prompt、shared 題庫或一般匯出。
- 代理與開發流程只看得到彙總分數與類別分數，不得看失敗題目細節。
- 建議只在重大 pipeline／prompt／retrieval 改動前後各跑一次；其他時間不查看題目內容，也不依結果調題。

## 2. 類別配額（建議 24 題）

| 類別 | 題數 | 設計重點 |
| --- | ---: | --- |
| 直接條文查詢 | 4 | 指定法規與條號，答案可從現行條文直接核對 |
| 語意改寫 | 4 | 不使用條號或正式用語，測 retrieval 是否找到正確法規 |
| 多條文比較 | 4 | 兩部以上法規／命令的競合、例外或適用順序 |
| 邊界與易混淆 | 4 | 相近概念、舊法／新法、容易引用錯誤條號 |
| 應拒答 | 4 | 非金融法規、超出資料範圍、要求法律意見或預測判決 |
| 日期與法院條件 | 2 | 指定裁判年份、法院或日期區間，測 filter 與引用範圍 |
| 統計與護欄 | 2 | 要求統計、排名或總數，預期被護欄攔截或明確說明限制 |
| **合計** | **24** | 可依時間增減，但每個類別至少 2 題 |

## 3. 每題必要欄位

- `question`：使用者自然問法，不提示答案。
- `question_type`、`difficulty`、`tags`：供類別分數與覆蓋統計。
- `expected_laws`／`expected_articles`：人工核對後的官方來源。
- `reference_answer`：簡短、可驗證的標準答案；不貼整段法規。
- `rubric`：至少包含引用正確性、答案完整性、拒答正確性。
- `source_note`：官方法規資料庫 URL、查詢日期、版本或生效日。
- `visibility=holdout`、`status=accepted`、`source=manual`。

## 4. 流程

1. 由人依類別配額撰寫題目與標準答案。
2. 另一個人或同一人隔日重新核對官方原文，修正引用與日期。
3. 以 `pending_review` 建立，完成 review 後改為 `accepted`／`holdout`。
4. 鎖定版本，記錄 `content_hash` 與建立日期。
5. 只在改動前後各跑一次 benchmark；保存 summary 與類別分數。
6. 將 summary 寫入面試用一頁式說明；不得貼出 holdout 題目或失敗明細。

## 5. 驗收

- [ ] 至少 20 題，涵蓋上表所有類別。
- [ ] 每題都有官方來源與人工核對紀錄。
- [ ] 題目不在 shared 題庫、Agent JSONL 或公開匯出中。
- [ ] benchmark 報告只顯示總分與類別分數。
- [ ] 題目版本與修改紀錄可追溯。
