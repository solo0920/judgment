# Feature Specification: 金融法規判決篩選

**Feature Branch**: 未建立（無 `before_specify` hook；以規格目錄 `003-law-cited-judgment-filter` 識別）

**Created**: 2026-11-06

**Status**: Partially implemented (filter, PostgreSQL import, versioned Qdrant collections and atomic alias switching; review queue and law alias maintenance pending)

**Input**: 使用者提供之需求（原文）：

> /Users/leesolomon/projects/judgment/documents/金融法規.md 以md檔所列之法規來作選擇，有當中的法規的判決才納入資料庫

**需求解讀**: 以 `documents/金融法規.md`（使用者提供的絕對路徑為 `/Users/leesolomon/projects/judgment/documents/金融法規.md`）作為法規白名單。判決必須明確引用清單中至少一項法規，才可納入資料庫與檢索索引；未引用清單法規的判決保留原始檔，但不進入索引。此功能補充 `001-judgment-rag-search` 的資料處理流程，並遵循 `002-judgment-data-storage` 的檔案儲存規範。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 只納入引用清單法規的判決 (Priority: P1)

資料管理員以 `documents/金融法規.md` 所列法規作為篩選條件。系統在建立索引與寫入資料庫前，先擷取每筆判決引用的法規；只要判決明確引用清單中至少一項法規，就納入後續流程；完全未引用清單法規的判決則排除於索引與資料庫之外。

**Why this priority**: 這是本功能的核心目的。若不先篩選，資料庫會混入大量與金融法規無關的判決，增加索引成本並降低檢索精確度。

**Independent Test**: 準備三筆測試判決：一筆引用「銀行法」、一筆僅引用「刑法」、一筆同時引用「民法」與「刑法」。執行篩選後，第一筆與第三筆應納入，第二筆應排除；再檢查排除原因與命中法規是否正確記錄。

**Acceptance Scenarios**:

1. **Given** 清單包含「銀行法」，**When** 判決明確引用「銀行法」第 1 條，**Then** 該判決具備納入資格，並記錄命中「銀行法」。
2. **Given** 清單不包含「刑法」，**When** 判決只引用「刑法」條文，**Then** 該判決被排除，且排除原因為「未引用清單法規」。
3. **Given** 判決同時引用清單內的「民法」與清單外的「刑法」，**When** 執行篩選，**Then** 判決納入一次，並記錄「民法」為命中法規。
4. **Given** 判決只提到法規名稱而沒有條號，或只是在假設、否定或引用他案時提及，**When** 執行篩選，**Then** 系統不自動納入，而是標記為待人工複核。
5. **Given** 清單檔案不存在、為空或沒有有效法規，**When** 啟動篩選，**Then** 系統中止作業、回報明確錯誤，且不變更現有索引。
6. **Given** 同一判決被多個清單法規命中，**When** 建立索引，**Then** 該判決只出現一次，且所有命中法規都可追溯。

---

### User Story 2 - 清單解析、名稱正規化與可追溯決策 (Priority: P2)

資料管理員能匯入並解析 Markdown 法規清單，系統正確處理全形/半形、空白、標點、書名號、舊名稱與範圍註記；每一筆納入或排除決策都能追溯到清單版本、引用文字與比對規則。

**Why this priority**: 法規名稱在判決中的寫法不一致，若比對不可追溯，將難以解釋漏納或誤納，也無法校正別名與人工複核。

**Independent Test**: 使用包含重複項目、空白行、全半形差異、舊法規名稱與括號範圍註記的清單，確認解析報告、正規化結果、別名套用與決策紀錄皆正確。

**Acceptance Scenarios**:

1. **Given** 清單有 99 行且包含空白行與重複法規，**When** 解析清單，**Then** 系統忽略空白行、保留有效法規，並在報告中列出重複項目與行號。
2. **Given** 清單項目為「災害防救法（有關金融紓困部分）」，**When** 解析，**Then** 系統分離法規名稱「災害防救法」與範圍註記「有關金融紓困部分」。
3. **Given** 判決寫成「銀行法」、「銀行 法」或全形標點變體，**When** 比對清單，**Then** 系統以正規化後名稱判定為同一法規，並記錄原始引用文字。
4. **Given** 判決使用法規舊名稱或別名，**When** 別名對照表包含該名稱，**Then** 系統可正確比對，並在決策紀錄中標示使用的別名。
5. **Given** 比對結果不明確或只能模糊匹配，**When** 執行篩選，**Then** 系統不自動納入，而是放入人工複核佇列。
6. **Given** 任一納入或排除決策，**When** 管理者查詢，**Then** 可看到清單版本、判決識別、引用文字、使用規則、篩選作業與時間。

---

### User Story 3 - 清單更新與重新篩選 (Priority: P3)

管理者更新 `documents/金融法規.md` 或別名對照後，可先試跑查看影響，再重新篩選。新符合的判決加入索引，不再符合的判決從搜尋索引移除；切換採新索引版本原子生效，不中斷查詢。

**Why this priority**: 法規清單會隨政策與業務調整；沒有安全的重新篩選機制，將難以維護資料範圍，但核心篩選可在初始匯入時獨立運作。

**Independent Test**: 修改測試清單，新增一項法規並移除一項法規，執行試跑與套用，確認新增與移除的判決正確、舊索引在切換前仍可查詢、切換後不再出現被移除的判決。

**Acceptance Scenarios**:

1. **Given** 清單已變更，**When** 管理者執行試跑，**Then** 系統顯示預計納入、排除、待複核數量與各法規命中數，且不變更現有索引。
2. **Given** 試跑結果已確認，**When** 管理者套用重新篩選，**Then** 系統建立新索引版本，新符合者加入、不再符合者移除，並以原子切換生效。
3. **Given** 重新篩選正在建立新索引，**When** 一般使用者查詢，**Then** 系統仍以舊索引提供服務，且不會出現新舊資格混合的結果。
4. **Given** 判決因清單變更而被排除，**When** 檢查檔案系統，**Then** 其原始檔與稽核紀錄仍保留於 `/data/judgments`，不得被刪除。
5. **Given** 重新篩選中斷，**When** 再次執行，**Then** 系統可續跑或重跑，且不產生重複索引項目。
6. **Given** 已有篩選作業進行中，**When** 另一位管理者觸發篩選，**Then** 系統拒絕或排隊，不得同時執行兩個篩選作業。

---

### Edge Cases

- 清單檔案不存在、不可讀、編碼錯誤、為空或全部是空白行時，系統如何處理？
- 清單包含重複法規、只有括號註記、名稱過短或明顯不是法規名稱時，如何辨識與回報？
- 判決引用法規舊名稱、簡稱、別名，或同一法規因修正而有不同名稱時，如何比對？
- 判決使用「本法」、「該法」、「同法」等相對用語時，如何判定所指法規？
- 判決只提到法規名稱而沒有條號，或只在引用他案、假設語氣、否定適用時提及，是否算引用？
- 判決引用標註範圍的法規（例如「災害防救法（有關金融紓困部分）」），但引用條文無法判定是否落在範圍內時，如何處理？
- 同一判決同時引用多項清單法規時，如何避免重複納入？
- 清單在篩選進行中被修改時，如何確保本次作業使用一致的清單版本？
- 重新篩選後，原本已索引的判決不再符合資格時，如何避免舊索引仍回傳該判決？
- 篩選作業中斷或服務重啟時，如何避免半寫入索引或重複資料？
- 人工複核佇列累積過多項目時，是否有優先順序與批次處理方式？
- 清單包含已廢止或名稱已變更的法規時，舊判決是否仍可納入？

## Requirements *(mandatory)*

### Functional Requirements

#### 清單來源與解析

- **FR-001**: 系統 MUST 以 `documents/金融法規.md` 作為預設法規清單來源；管理者 MUST 能設定替代路徑，且每次篩選使用一個明確的清單版本。
- **FR-002**: 清單格式 MUST 支援 UTF-8、每行一項法規、忽略空白行；系統 MUST 保留原始行號以供追溯。
- **FR-003**: 系統 MUST 解析法規名稱後方括號中的範圍註記（例如「災害防救法（有關金融紓困部分）」），並分離法規名稱與範圍註記。
- **FR-004**: 系統 MUST 偵測重複、空白、無法解析或可疑的清單項目，並產出包含行號的解析報告；不得靜默忽略。
- **FR-005**: 系統 MUST 為每次使用的清單建立版本識別，至少包含內容雜湊、有效項目數與建立時間；清單變更不得覆蓋舊版本紀錄。
- **FR-006**: 清單檔案不存在、不可讀、為空或沒有有效法規時，系統 MUST 中止篩選且不變更現有索引。

#### 判決引用擷取與比對

- **FR-007**: 系統 MUST 從判決中擷取法規引用，至少包含法規名稱與條號；來源可為結構化引用欄位或判決全文。
- **FR-008**: 系統 MUST 對法規名稱與引用文字執行正規化，至少處理全形/半形、空白、標點、書名號與常見前綴。
- **FR-009**: 系統 MUST 以正規化後的名稱與清單比對；比對規則必須確定性、可重現，且相同輸入產生相同結果。
- **FR-010**: 判決 MUST 至少有一筆引用符合清單法規，才具備納入資格。
- **FR-011**: 系統 MUST 記錄每筆判決的納入決策，包含符合的法規、原始引用文字、使用的規則、清單版本、別名版本與篩選作業識別。
- **FR-012**: 判決引用多項清單法規時，系統 MUST 只納入一次，並記錄所有符合的法規。
- **FR-013**: 判決僅提及法規名稱而無條號，或僅在非裁判依據的語境中提及時，系統 MUST 不自動納入，並標記為待人工複核。
- **FR-014**: 系統 MUST 支援法規別名與舊名稱對照；別名 MUST 可由管理者維護，且每次套用都必須留下紀錄。
- **FR-015**: 模糊或不明確的比對 MUST 不得自動納入，必須進入人工複核佇列。
- **FR-016**: 標註範圍的法規 MUST 依引用條文與上下文判斷是否落在範圍內；無法判定時 MUST 進入人工複核，預設不自動納入。
- **FR-017**: 系統 MUST 保存被排除判決的排除原因與可追溯資訊，不得只記錄「未納入」。

#### 篩選作業與索引

- **FR-018**: 篩選 MUST 在建立檢索索引與寫入資料庫之前執行，使不符合資格的判決不進入索引與資料庫。
- **FR-019**: 篩選作業 MUST 支援完整重跑與增量重跑，且可於中斷後續跑。
- **FR-020**: 同一時間 MUST 只允許一個篩選作業；並行請求 MUST 排隊或拒絕。
- **FR-021**: 系統 MUST 支援試跑模式，顯示預計納入、排除、待複核數量與各法規命中數，且在管理者確認前不變更索引。
- **FR-022**: 清單或別名變更後，系統 MUST 重新計算資格；新符合者納入，不再符合者自搜尋索引移除。
- **FR-023**: 資格變更 MUST 透過建立新索引版本並原子切換生效；切換前舊索引仍可查詢，切換期間不得出現混合新舊資格的結果。
- **FR-024**: 被排除判決的原始檔與稽核紀錄 MUST 保留（依 `002-judgment-data-storage` 的規範），不得因排除而刪除。
- **FR-025**: 系統 MUST 支援至少 100,000 筆判決的單次篩選作業，並可重複執行而不產生重複索引項目。
- **FR-026**: 系統 MUST 提供篩選結果摘要，至少包含清單版本、作業識別、總判決數、納入數、排除數、待複核數、各法規命中數、耗時與狀態。
- **FR-027**: 系統 MUST 提供人工複核佇列，讓管理者核准或駁回待複核判決；決策必須記錄人員、時間與理由，並於下次篩選套用。
- **FR-028**: 系統 MUST 提供查詢目前清單版本、最近一次篩選作業、索引版本與各法規納入判決數的管理介面。
- **FR-029**: 篩選作業 MUST 產生 JSON 效能紀錄，包含清單解析、引用擷取、比對、複核套用、索引建立與切換各階段耗時、總耗時、處理數量與架構／設定版本。
- **FR-030**: 篩選失敗時，系統 MUST 保留現有索引與資料，標示失敗階段與原因，並允許重試。
- **FR-031**: 只有授權管理者能修改清單、別名、執行篩選或變更索引；一般使用者不得操作。
- **FR-032**: 系統 MUST 記錄清單變更、別名變更、篩選執行、索引切換與人工複核的稽核事件。

### Key Entities *(include if feature involves data)*

- **法規清單 (Law List)**: 來自 `documents/金融法規.md` 的法規集合；包含版本識別、內容雜湊、有效項目數、建立時間與來源路徑。
- **法規清單項目 (Law List Entry)**: 清單中的一項法規；包含原始行號、原始文字、法規名稱、範圍註記、正規化名稱與狀態（有效／重複／可疑）。
- **法規別名 (Law Alias)**: 法規舊名稱、簡稱或變體與正式法規名稱的對照；包含生效期間、來源與維護紀錄。
- **判決引用 (Judgment Citation)**: 判決中的一筆法規引用；包含所屬判決、引用文字、法規名稱、條號、段落位置與正規化結果。
- **資格決策 (Eligibility Decision)**: 一筆判決的納入結論；包含納入／排除／待複核、命中法規、使用規則、清單版本、別名版本與篩選作業識別。
- **篩選作業 (Filter Run)**: 一次篩選執行；包含清單版本、別名版本、試跑或正式、處理數量、各類計數、耗時、狀態與錯誤資訊。
- **人工複核項目 (Review Item)**: 需要人工判斷的引用或判決；包含原因、引用文字、建議、複核者、決策、理由與時間。
- **索引版本 (Index Version)**: 一組具備資格的判決與其索引產物；包含版本識別、建立時間、生效狀態與對應的篩選作業。
- **篩選效能紀錄 (Filter Performance Record)**: 篩選各階段耗時、總耗時、處理數量、架構／設定版本與結果狀態，以 JSON 表示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 索引稽核結果顯示 100% 的已索引判決至少命中一項清單法規，且 0 筆未命中清單的判決進入索引或資料庫。
- **SC-002**: 在至少 500 筆由人工標註的判決驗證集中，誤納入數為 0，且符合資格判決的納入召回率至少 98%。
- **SC-003**: 100% 的有效清單項目都能被解析；重複、空白與可疑項目 100% 在報告中列出並附行號。
- **SC-004**: 100% 的納入與排除決策可追溯至判決、引用文字、法規清單版本與篩選作業識別。
- **SC-005**: 100,000 筆判決的試跑或正式篩選可在 1 小時內完成。
- **SC-006**: 清單變更並重新篩選後，不再符合資格的判決在索引切換後 100% 不再出現於搜尋結果，且切換期間查詢服務停機時間為 0。
- **SC-007**: 100% 的範圍註記法規在無法判定引用範圍時進入人工複核，且未被自動納入。
- **SC-008**: 管理者能在 1 分鐘內取得目前清單版本、最近一次篩選結果、索引版本與各法規納入判決數。
- **SC-009**: 清單缺漏、為空或無有效法規時，篩選作業 100% 中止，且索引變更次數為 0。
- **SC-010**: 100% 的篩選作業產生有效的 JSON 效能紀錄，且包含各階段與總耗時。
- **SC-011**: 重複執行同一份清單與判決資料時，重複索引項目數為 0，且兩次決策結果一致。
- **SC-012**: 100% 的別名套用與人工複核決策都有稽核紀錄；未記錄的別名套用次數為 0。
- **SC-013**: 100% 的人工複核決策在下一輪篩選中被套用，且可追溯至複核者、時間與理由。
- **SC-014**: 因篩選而排除的判決，其原始檔 100% 仍保留於 `/data/judgments`，刪除數為 0。
- **SC-015**: 同時觸發多個篩選作業時，僅 1 個作業執行，測試後索引損壞或重複項目數為 0。

## Assumptions

- `documents/金融法規.md` 為 UTF-8 文字檔，每行一項法規；目前共有 99 行，其中包含 3 項帶有括號範圍註記的法規。清單內容由使用者或管理者維護，系統不負責判斷某項法規是否屬於金融法規。
- 「有當中的法規」定義為判決明確引用清單法規的名稱與條號。僅提及法規名稱、引用他案、假設語氣、否定適用或無法確認裁判依據的提及，不自動視為符合資格，而是進入人工複核。
- 帶有範圍註記的法規，只有在引用條文與上下文可判定落在註記範圍內時才自動納入；無法判定時進入人工複核，預設不自動納入。
- 法規名稱比對以正規化後的精確比對與管理者維護的別名對照為主；模糊比對僅產生複核建議，不得自動納入。
- 「本法」、「該法」、「同法」等相對用語，若可從上下文判定所指法規，則納入比對；無法判定時進入人工複核。
- 清單可能包含已廢止、修正或改名之法規；舊判決仍可依當時名稱或別名比對，別名與版本必須留下紀錄。
- 被排除判決的原始檔仍保留於 `/data/judgments`，符合 `002-judgment-data-storage` 的儲存規範；篩選只影響是否進入索引與資料庫。
- 篩選在建立檢索索引與寫入資料庫之前執行，以降低不必要的處理成本。
- 既有已索引資料在首次啟用本功能時需要執行一次完整重新篩選。
- 系統設計支援至少 100,000 筆判決的單次篩選與總量 100 萬筆的資料集；人工複核產能由管理者安排。
- 判決引用的擷取以判決中的結構化引用欄位或全文規則為基礎；若來源格式不足，系統將無法判定的案例交由人工複核。
- 篩選作業與既有 `001-judgment-rag-search` 的效能紀錄、索引切換與管理權限機制整合。

## Out of Scope

- 由系統自動判斷判決是否「重要」、是否具代表性或是否應公開。
- 自動維護或修改 `documents/金融法規.md` 的內容；清單由管理者編輯。
- 依案件類型、法院、裁判日期或裁判結果進行篩選。
- 將法規名稱翻譯為其他語言。
- 以大型語言模型自動判定判決是否屬於金融法規範疇。
- 刪除被排除判決的原始檔或稽核紀錄。
- 判斷法規本身是否屬於金融法規，或審查清單內容的法律正確性。

## Implementation Note (2026-11-09): 版本化索引與 Alias

已補上 FR-023 的第一階段能力：

- Qdrant 使用 `judgments_vNNN` 實體 collection，正式查詢使用 `judgments_current` alias。
- 新版本建置時不修改 active collection；完成驗證後才以 Qdrant `POST /collections/aliases` 原子切換。
- `judgment_index_versions` 記錄版本、collection、alias、embedding model／version、維度、來源 snapshot、驗證結果、狀態、前後版本與時間。
- `judgment_vector_index` 改為 `(jid, version_id)` 複合主鍵，並記錄 `index_text_hash`、`payload_hash`、`source_year`、`source_updated_at`。
- 相同 embedding model／dimension／index recipe 時，新版本會複製舊 collection 的 points，只重新 embedding 新增、異動或 metadata 變更的判決；已移除判決會從新 collection 刪除。
- 驗證包含 PostgreSQL per-version count、Qdrant exact count、dimension 與 collection 可讀性；驗證失敗不得切換。
- 保留 active＋前一個成功版本，支援 alias rollback；第一階段不自動刪除舊 collection。
- 仍待完成：人工複核佇列、法規別名維護、正式 UI 管理介面、自動 retention、完整篩選效能紀錄。
